# Threat model

Principle: models only produce data that is validated and shown to the user; they never run
actions (ADR-0007). Only four things are reachable from outside: the Telegram bot (owner
only; invited members too once ADR-0059 is built and `TC_MULTI_USER` is on), the dashboard (Cloudflare), the band data ingest endpoint (Cloudflare, ingest secret,
ADR-0055), and in phase 3 the MCP endpoint (Cloudflare, OAuth).

## Assets

Workout history, body measurements and photos (personal; other people's too once members exist), bot token, Groq key, Claude OAuth
token, session cookies, the Pi itself (shared with Vybe).

## Threats and controls

| Threat | Entry point | Controls | Tests / checks |
| --- | --- | --- | --- |
| T1: Strangers using the bot | Telegram commands, button presses and typed text | Commands carry the `owner_only` filter; typed text combines it with `TEXT & ~COMMAND`; it answers a pending /settings question or is parsed as a workout log by the bounded rule parser and shown for confirmation before anything is saved (ADR-0007); log buttons carry only a random draft token; button presses (which can't take a filter) check the sender first and get no answer otherwise. Queue buttons name their session and are re-checked against the queue; settings buttons carry the value they set, so an old or forged press can't act on another session or flip a setting the wrong way | Stranger tests for every command, button and typed text (`tests/bot/`); stale-button tests |
| Voice notes leave the Pi | Voice -> Groq transcription | Only the owner's voice notes are sent (owner filter), with the plan's exercise names as a spelling prompt; capped at 2 min / 5 MB and refused if the size is unknown; a 45 s deadline per transcription; held in memory only, never written to disk; transcripts shown to the owner but never logged; dedicated Groq key; voice is off until the key is set | Voice tests: strangers ignored, transcript and key absent from logs, caps refused before download |
| Prompt injection in a log | Voice/text -> rule parser (and the model fallback, #59) | Owner-only bot; transcripts and text reach only the bounded rule parser; the model fallback gets no tools, answers a strict schema whose names are an enum of the plan, and its output is re-parsed by the same rules and used only if clean (ADR-0023); confirm before save | Parser hostile-input tests; hostile transcript test (`tests/bot/test_voice.py`); invented, extreme, smuggled and injected model answers (`tests/bot/test_model_fallback.py`) |
| One person seeing or changing another's data (ADR-0026) | Every per-person table | Sessions are bound to a user (ADR-0029): every ORM select and delete on an owned table (sets included) is filtered to that user, new rows are stamped with them, and writing another user's row, a set on another's workout, changing a row's owner, or a bulk insert/update raises. An unbound session refuses to read or bulk-change per-person rows unless a shared check asks for every user explicitly; rows it adds must name their user. String SQL and `session.connection()` are not covered and not used for per-person data. The bot's sessions are bound to the owner, linked to the allowed Telegram account. Until invites exist there is one user | Two-user scope tests (`tests/db/test_user_scope.py`): reads, sets alone, lookups by id, cached statements, refused writes, bulk deletes; per-user seed test |
| Planned (ADR-0059): someone joining with an invite meant for another person, or guessing, replaying or flooding invites; members getting in while multi-user is off | `/join#token`, the invites table | Nothing opens while `TC_MULTI_USER` is off (the default): invites can't be made or redeemed; members can't link Telegram or get messages, and can sign in only to an export-only Account page (export, or leave now) until their data is erased 30 days later by the wind-down job (ADR-0059). Only the admin makes invites; at most `TC_MAX_MEMBERS` people. Token of 32 random bytes in the URL fragment, stored as SHA-256, single use (claimed by one conditional update), 72 hours, revocable from the admin's list; rate limited per address like the sign-in options. An invite makes a member, never an admin. Redeeming shows the notice, checks the person is an adult, and asks for a passkey at once; the admin is told when an invite is used | To be written with the invites step: single use, expiry, revoke, the cap, switch off with a member in the database: only export and leave answer, and the wind-down job erases them after 30 days |
| Planned (ADR-0059): a stranger linking their Telegram to someone's account; the owner's configured Telegram account taking a member's link; one person's update handled with another's session | The Account "Connect Telegram" link, `/start <token>`, the owner's relink at start-up | A connect token is made only by a signed-in person: 32 random bytes, stored hashed, single use, 10 minutes; `/start <token>` is the only thing a stranger reaches, rate limited, private chats only; one Telegram account per person (unique). At start-up `TC_TELEGRAM_ALLOWED_USER_ID` links the owner only if no one else holds that account; otherwise it logs an error and keeps the existing link. Every update gets a session bound to the person found from its sender; unlinking is on Account and leaving or erase removes the link | To be written with the Telegram step: two linked members each see only their own `/today`, logs, buttons and drafts; a press carrying the other's draft token is refused; each scheduled message reaches its own person with their own data |
| Planned (ADR-0059): the admin seeing a member's data; a member acting as admin; an admin recovery link used to take over a member | Admin page and routes, admin recovery link | A `role` column; the owner is the only admin. Admin routes depend on an admin check on top of the signed-in person, declared as a fourth kind in the route-access test; their answers hold counts, labels and join days only, and no route reads another person's data. A recovery link: single use, 24 hours, signs out the member's other browsers, removes their passkeys; not redeemable from a browser signed in as an admin; the member is alerted when it is made and when it is used, and Account shows them a recovery notice for 30 days that can't be dismissed (ADR-0059). Removing a member comes after telling them and offering the export. Residual: whoever runs the Pi can read the database and backups, and the admin can take over a member's account with a recovery link (the member sees it afterwards); the privacy notice says both | To be written with the roles step (admin kind, counts-only answers) and the recovery step: an admin session can't redeem, both alerts sent, the notice can't be dismissed for 30 days |
| Prompt injection, token theft and the rest of connecting an AI over MCP | Phase 3 MCP (ADR-0047 C) | See [mcp-threat-model.md](mcp-threat-model.md): read scopes, and `propose_log` that only proposes (ADR-0058); no tool touches the plan, settings or sign-in | As listed there |
| Injected instructions in issues/PRs | Claude GitHub Action | OWNER-only triggers; no forks; no `pull_request_target`; restricted tools; secrets never in prompts | Workflow review in PRs |
| Secret leakage | Repo, logs, chats | `.env` ignored; gitleaks pre-commit + CI; Claude Code denied `.env`; `SecretStr`; httpx URL logging silenced | CI gitleaks; config repr test |
| Web attacks | Web app | Cloudflare WAF + rate limits on `/api/auth/*`; sign-in by a one-time bot link (owner-only `/login`, 32 random bytes, single use, 10 minutes, token in the URL fragment, stored as SHA-256) and later passkeys (ADR-0036); session cookies (`__Host-`) of 32 random bytes, stored hashed, HttpOnly/Secure/SameSite=Strict, 30 days renewed by use but never beyond 90 days from sign-in, ended at sign-out; removing a passkey ends the other sessions it started; changes refused unless `Origin`/`Sec-Fetch-Site` say they come from the app's own pages (SameSite alone would trust sibling `vybe-dev.com` sites); bodies over 64 KB refused before reading (photos have their own 3 MB cap); personal API answers `Cache-Control: no-store`; database errors never show bound values; every route declared public or owner-only; CSP and security headers; ORM only | Security header test; `tests/api/test_request_guard.py`; `tests/services/test_auth.py`, `tests/api/test_auth.py` (single use, expiry, hashing, cookie flags, sign-out, every route's access); `/login` stranger test |
| Fingerprinting the app: its version (to match known flaws) and whether the bot is on | `GET /healthz` (public) | A request through the tunnel carries `CF-Connecting-IP`, which Cloudflare adds to every request it passes on and a visitor can't remove; such a request gets only `{"status":"ok"}`. The version and bot state go only to callers on the Pi (the deploy timer, the heartbeat, Docker's health check), which call the app directly, not through the tunnel (security review, 2026-10-24). A visitor adding the header only hides more. **Residual:** this relies on the port being reachable only on the Pi or through the tunnel (published on 127.0.0.1, see deploy runbook), and on Cloudflare sending the header: its "Remove visitor IP headers" setting would show the version again (and break the per-address limits) | `tests/api/test_app.py` (`test_healthz_*`) |
| Someone with Liam's Telegram (unlocked phone, another session) | `/login`, `/recover` | Once a passkey exists a link alone doesn't sign in (ADR-0040); `/recover` works but signs out every other browser, removes every passkey and alerts; adding or removing a passkey needs a sign-in from the last 10 minutes; every sign-in and passkey change is alerted on Telegram; the bot answers only in its private chat | `tests/api/test_sign_in_hardening.py`, `tests/bot/test_login.py` |
| Stolen sign-in link | A `/login` message seen by someone else | Works once, for 10 minutes, claimed by one conditional update so two racing redeems can't both win; a used or expired link is refused; the token never reaches server or proxy logs (fragment) | Single-use, two-session and expiry tests |
| Passkey sync account taken over | The Google or Apple account that syncs passkeys | That account's own protection (2FA); passkeys can be listed and removed (device settings, #115); `/login` (Telegram) recovers access | Passkey tests |
| Flooding the public sign-in options, or using them up to lock the owner out | `/api/auth/passkeys/sign-in/options` (each call is a database row) | At most 5 open sign-in challenges per client address (CF-Connecting-IP, believed only from `TC_TRUSTED_PROXIES`: loopback and Docker's bridge 172.16.0.0/12 by default, not home networks; a direct caller counts as its own address; stored hashed; uvicorn never believes `X-Forwarded-For`, which a visitor can set). This assumes the app's port is reachable only through the tunnel (published on 127.0.0.1, see deploy runbook) and 200 overall, 429 beyond; expired ones cleared on each call; Cloudflare rate limit on `/api/auth/*`. A distributed flood can still fill the overall cap for up to 5 minutes; `/login` (Telegram) signs in regardless | Per-client and overall cap tests |
| Forged or replayed passkey sign-in | `/api/auth/passkeys/*` | The `webauthn` library verifies every ceremony: origin and RP ID from `TC_PUBLIC_URL`, the signature with the stored public key, user verification required (fingerprint or face, not a tap); challenges are random, single use (taken by a conditional delete), 5 minutes, named by an HttpOnly cookie; a registration challenge belongs to the signed-in user who asked for it; a key already registered is refused; any malformed answer is a 401, never a 500 | `tests/api/test_passkeys.py` with a software device: register then sign in, tap-only refused, unknown key, wrong origin, replay, expiry, wrong ceremony, garbled answer |
| Location or other metadata leaking in a progress photo | `PUT /api/photos/{day}/{pose}` | The browser shrinks and re-encodes; the server keeps only an allowlist of JPEG segments (frames, tables, scan headers and data, restart interval, Adobe colour), walks every scan and stops at the first end marker, so EXIF/GPS, XMP, comments, JFIF/JFXX thumbnails, trailers and anything after the picture are dropped; 3 MB cap; owner-only, `no-store` (ADR-0039) | `tests/domain/test_photos.py`, `tests/api/test_photos.py` |
| Body measurements, photos or daily checks reaching logs or caches | `/api/body`, `/api/photos`, `/api/daily-check` | Never logged (tests check captured logs); daily checks (ADR-0053) kept a year, never on the `/share` picture, in the export and erased with everything; database errors hide values; `no-store` on every API answer | `tests/api/test_body.py`, `tests/api/test_photos.py`, `tests/api/test_request_guard.py` |
| Another person's home kit read or changed; a kit note faking instructions to the person's AI; an oversized or endless kit (ADR-0071, ADR-0072) | `GET`/`PUT /api/equipment`, `GET /api/equipment/unlocks`, the `equipment` table | Owner-only routes; `equipment` is an `Owned` table, read and written only through the person's bound session (ADR-0029), so the home kit behind locks, unlocks and the next weight owned is always their own. A save replaces the whole list and is refused whole if any item doesn't fit: at most 60 items, each kind from a fixed list, weights 0.5 to 100 kg in steps of 0.5 (also check constraints), a range only on dumbbells and lighter to heavier, no item twice; `add` on unlocks is at most 40 characters and parsed by the same rules. A note is at most 40 characters of one line of plain text (no control, format or separator characters), so it can't fake a heading where the AI summary and MCP `get_summary` list the kit, and the summary puts each item on one line whatever is stored; React renders it as text. The `unlock` notes on Progress and the set screen are built on the server from kit names and weights only, never an item's note. The weights owned are walked from an adjustable set's lightest in the person's own step, at least 0.25 kg (a check constraint), so the walk ends. Logs carry the item count only; in the export, erased with everything; never on the `/share` picture | `tests/api/test_equipment_api.py` (needs a signed-in browser, a bad list refused whole), `tests/domain/test_kit.py` (notes on one line, weights and ranges), `tests/services/test_ai_summary.py` (a note stays on one line), `tests/domain/test_load.py` (the weights owned, the unlock), `tests/db/test_user_scope.py` (`equipment` is per person) |
| Forged, flooded or oversized band data; band data reaching logs (ADR-0055) | `POST /api/ingest/health-connect` (public; the Health Connect Webhook app on the phone) | Only a per-person ingest secret signs it in (`Authorization: Bearer`, 32 random bytes, shown once, stored as SHA-256, compared with `compare_digest`; made or replaced on Account within 10 minutes of a sign-in and alerted on Telegram); cookies neither read nor set; per address at most 60 calls and 10 wrong secrets per 10 minutes, per secret at most 20 (429); at most two posts parsed at once (503), so parallel posts stay inside the container's 512 MB; body read to 5 MB and no further, a larger declared length refused before reading; a post read for at most 100 workouts, 50 nights and similar caps per type (ADR-0055, 2026-10-24); Today offers the newest 30 workouts and Telegram sends at most 12 for two days; max heart rate rises only with what a workout held 3 minutes, at most 20 bpm over the estimate, and the person is told on Telegram when it moves; a lone surrogate is refused (422); the app version is stripped of control and bidi characters. **Residual:** whoever holds the secret can write band data within these bounds, and made-up steps (up to 200,000 a day) or resting heart rate (down to 25) stick, because a day keeps its larger steps and lower resting rate; the fix is a new secret on Account and correcting the day; the secret is checked before the body is read; every record validated with bounds and skipped if it fails; times older than 30 days or in the future dropped; raw payloads never stored; logs carry counts per type only; per-minute heart rate kept 8 days; in the export, erased with everything | `tests/api/test_ingest.py`, `tests/services/test_health_import.py`, `tests/services/test_ingest_keys.py` |
| The band reader's secret or signing key leaking; the reader sending health data anywhere else (ADR-0070) | `android/`, the phone, the GitHub environment `android-release` | The ingest secret is typed once in a password field (screenshots blocked), encrypted with an AES key held in the Android Keystore and never shown again; app data is never backed up (`allowBackup=false`, `no_backup.xml`); HTTPS only, to the coach's ingest address built into the app and checked (host, path, no user part or port), never typed, redirects not followed, cleartext off; reads Steps and Heart rate only, writes nothing to Health Connect; no third-party SDKs or analytics. The release signing key exists only as secrets of the `android-release` environment, which needs Liam's approval for every run and deploys from protected branches only, plus an age-encrypted backup off GitHub; it never meets Gradle or its dependencies (the build job makes an unsigned APK with no secrets, the release job only runs apksigner and checks the certificate digest pinned in `android/SIGNING_CERT_SHA256`); checkouts keep no token. Gradle dependency verification (`android/gradle/verification-metadata.xml`, sha256, written in CI and committed) fails the build when a plugin or library differs from its recorded checksum, so a swapped build dependency can't alter the unsigned APK before it is signed. Accepted residual risk: the checksums trust what the repositories served when they were written (separate runs compared before committing); a leaked key would let someone ship an update, fixed only by a new package name and reinstall | `android/app/src/test/.../PayloadTest.kt` (only the coach's address, look-alikes refused; the body's shape); the release job checks the APK's signer; `android.yml` fails on a wrong checksum |
| Share-link abuse | Share URLs | 32-byte random, hashed at rest, expiry, revocable, read-only, no measurements/photos | Share view tests |
| Container escape / lateral movement to Vybe | App container | Non-root, read-only FS, cap_drop ALL, no-new-privileges, own network, localhost-only port | Compose review |
| Host compromise | Pi | SSH over Tailscale only; firewall deny inbound; unattended security upgrades | Deploy runbook checklist |
| Supply chain | PyPI, npm, Actions | Lockfiles; Dependabot; pip-audit + npm audit; Actions pinned to SHAs; CodeQL (a required check, failing on new alerts) | CI security job |
| A release that didn't come through a pull request | The Pi's automatic deploy | Branch protection, enforced for admins: a required pull request and required checks (CodeQL included). On the Pi, a second check: it deploys only tags on `main` whose commit carries a good signature by GitHub's pinned key, so not a plain `git push` (ADR-0043). Residual: a stolen token with write access can make a GitHub-signed commit through the API, so the token scopes and branch protection carry that; the key and fingerprint come from the checkout already deployed; a refused release alerts | `tests/test_auto_deploy.py` (unsigned, someone else's key, bad signature, no gpg) |
| Use from outside the EU and EEA, which the app doesn't serve (ADR-0085), or a forged country to get past the check | Every route but the machine paths | Layer 1, Cloudflare: a WAF custom rule blocks other countries (applied by hand, `docs/runbooks/deploy.md`). Layer 2, the app (`api/region.py`): `CF-IPCountry` is believed only from `TC_TRUSTED_PROXIES`, exactly like `CF-Connecting-IP`, so a caller reaching the port another way (LAN, Tailscale) can't name a country; outside the 37 codes, and `XX` (unknown) and `T1` (Tor), a browser route gets 451 and an API call 451 JSON, which the web app shows as the same page; for `XX` and `T1` the page says it can't tell where the visitor is (Tor, some VPNs), never a silent failure. **Fails open:** a request with no country from a trusted proxy (local development, tests, the container's health check, a process on the Pi, a missing Cloudflare header) is let through, so a header that stops coming can't lock the owner out; the runbook says to check it arrives. **Exempt, reachable from anywhere:** `/mcp`, `/oauth/token`, `/oauth/register`, `/.well-known/oauth-*` (an AI app's servers call them from the US, ADR-0054) and `/healthz`, so their own checks carry the whole burden: the bearer token and per-connection limit on `/mcp`, PKCE, client and per-address limits on OAuth (`mcp-threat-model.md`); `/healthz` tells the tunnel only `{"status":"ok"}`. The consent steps (`/oauth/authorize`, `/connect`, `/api/connect/*`) are not exempt. **Residual:** a VPN or proxy in Europe passes both layers (Cloudflare advises IP location not be the only signal for compliance) | `tests/api/test_region.py`, `tests/domain/test_region.py`, `test_every_route_is_public_or_owner_only` (only the exempt routes skip it), `frontend/src/region.test.tsx` |
| Bot token theft | Telegram | Allowlist blocks data access; rotate via BotFather | Rotation runbook |
| Everything taken at once through the data export | `GET /api/account/export` (a zip of all data and photos) | Owner only, and only within 10 minutes of a sign-in, like passkey changes; alerted on Telegram and recorded as an `account.exported` event; sign-in secrets left out by rule (every binary column, every `*_hash` column, `credential_id`), so a column added later isn't exported by default; only the signed-in person's rows | `tests/api/test_export.py` |
| Everything erased by someone else, or by a slip | `POST /api/account/erase` | Owner only, within 10 minutes of a sign-in, with the word typed; alerted on Telegram; the latest nightly backup can restore it for a few weeks (ADR-0044) | `tests/api/test_erase.py` |
| A person's own AI key read from a leaked database or backup; or swapped for someone else's, so their data goes to another account | `ai_connections`, `PUT /api/account/ai/key` (ADR-0047 B) | Stored only as a Fernet token under `TC_SECRETS_KEY` (in `.env`, not in the database or backups); binary, so the export leaves it out; never logged or sent back (last four characters only). Checked with Groq before it is kept; only `gsk_` keys accepted. Storing one needs a sign-in in the last 10 minutes and is alerted on Telegram. Rotation without re-entry (`rotate-secrets`). Does not protect against a compromised Pi, where `.env` sits beside the database | `tests/api/test_ai_key.py`, `tests/services/test_secret_box.py`, `tests/services/test_ai_key.py` |
| The weekly AI comment (untrusted LLM text) injecting markup or links into the web review, staying longer than needed, or leaking through a share | `ai_comments`, `GET /api/review`, `/review` (ADR-0056) | Cleaned before it is sent or kept (no control characters, links, @mentions or /commands; 1,200 characters at most, also a check constraint); returned as a plain string and rendered by React as text, never HTML or markdown; labelled as a suggestion from the person's key; never acted on. Kept 7 days: older rows deleted at each weekly review and on every store, never returned after 7 days; shown only while comments are on. Owner-only route; in the export, erased with everything; never on the share picture, in "Copy for my AI" or MCP answers. Still one Groq call per weekly review; the page never calls Groq | `tests/services/test_ai_comment.py`, `tests/api/test_review_api.py`, `tests/services/test_share_card.py`, `frontend/src/review/ReviewPage.test.tsx` |
| Data loss | SD card | WAL, nightly backups, an encrypted off-site copy (ADR-0042; running since 2026-10-25, when the restore drill found it had never run), restore drill; a failed deploy or off-site run alerts on Telegram (`training-coach-alert@.service`), and the off-site job pings its own Healthchecks.io check, so one that stops running is noticed; a desktop copy is not set up yet; the Pi or app going down alerts through a Healthchecks.io heartbeat (ADR-0045) | Restore rehearsal per release |
